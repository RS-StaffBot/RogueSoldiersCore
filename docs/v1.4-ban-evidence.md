# v1.4.0 Ban Evidence

## Purpose

This document records the sanitized live evidence used to approve deterministic Provider completion for the 7 Days to Die `ban add` operation.

The evidence was captured against 7 Days to Die V3.1.0 b13.

## Approved Command Shape

```text
ban add <durable user id> <duration> <unit> "<reason>" "<display name>"
```

Verified durable identifiers use one combined value such as:

```text
Steam_<platform user id>
EOS_<cross-platform user id>
```

The server does not accept `Steam` and the numeric user ID as separate arguments.

## Verified Success

A successful ban completes on:

```text
<stored user id> banned until YYYY-MM-DD HH:MM:SS, reason: <reason>.
```

The returned stored user ID may be the submitted Steam identifier or an EOS-normalized identifier, depending on whether the server resolves an online player identity.

The earlier `Kicking player (Banned until: ...)` log line is not the deterministic command terminal line.

## Verified Invalid Target

```text
"<target>" is not a valid entity id, player name or user id.
```

## Duplicate Behavior

Adding the same active ban again refreshes the existing entry. It does not create a duplicate row and is not rejected.

The newer command recalculates the expiry from the new execution time.

## Ban List Behavior

```text
Ban list entries:
  Banned until - UserID (name) - Reason
  YYYY-MM-DD HH:MM:SS - <stored user id> (<display name>) - <reason>
```

Expired temporary bans disappear from the active list automatically.

## Authentication Enforcement

An active ban is enforced during authentication before the player enters the world. Rejected connections remain at `EntityID=-1` and fail the `BansAndWhitelist` authorization step.

## Completion Boundary

The Provider completes `ban add` only on the verified success or invalid-target line.

Later output is excluded from the completed result, including:

- player disconnect events
- `serveradmin.xml` reload messages
- EOS cleanup errors
- disconnect warnings
- Unity stack traces

## Unban Evidence Boundary

The server prints a success-looking `removed from ban list` response even when the supplied identifier does not match the stored active entry.

A future unban operation must:

1. Read `ban list`.
2. Resolve the exact stored UserID.
3. Execute `ban remove <exact stored UserID>`.
4. Read `ban list` again.
5. Report success only after the entry is absent.

This behavior is documented for the later unban phase and is not implemented by the current ban-completion phase.
