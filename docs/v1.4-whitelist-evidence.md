# v1.4.0 Whitelist Evidence

## Purpose

This document records sanitized live evidence for individual 7 Days to Die whitelist administration.

The evidence was captured against 7 Days to Die V3.1.0 b13 through the private server console on July 30, 2026.

Real platform identifiers, private addresses, local file paths, player positions, inventory details, and unrelated server activity are omitted or replaced with placeholders.

## Verified Help Contract

The server reports these individual-user operations:

```text
whitelist add <name / entity id / platform + platform user id> [displayname]
whitelist remove <name / entity id / platform + platform user id>
whitelist list
```

Name and entity-ID targeting require the player to be online. A combined durable platform identifier can target an offline player.

Live testing proved that the platform and platform-user ID are supplied as one combined argument:

```text
EOS_<id>
Steam_<id>
```

Supplying the platform and identifier as separate arguments is rejected for having the wrong number of arguments.

## Approved Individual Add Contract

```text
whitelist add <Steam_...|EOS_...> <display name>
```

Verified success terminal line:

```text
<stored user id> added to whitelist.
```

When the first entry activates whitelist-only mode, the server may then print:

```text
Whitelist only mode has been ACTIVATED!
```

The success line is sufficient deterministic command completion. Activation, configuration reload, performance, entity, inventory, and other server lines are later output and are not part of the completion rule.

Adding an already-listed identifier prints the same add-success line, does not repeat the activation line, and does not create a duplicate list entry.

## Approved Individual Remove Contract

```text
whitelist remove <Steam_...|EOS_...>
```

Verified success terminal line:

```text
<stored user id> removed from the whitelist.
```

When removing the final entry, the server prints this line before the removal-success line:

```text
Whitelist only mode has been DISABLED!
```

The command must wait for the removal-success line rather than completing on the mode line.

Verified missing-entry terminal line:

```text
<stored user id> was not on the whitelist.
```

Both the success and missing-entry lines are deterministic completion outcomes. Discord formatting and business interpretation remain future work.

## Verified List Output

Empty whitelist:

```text
No users or groups on whitelist, whitelist only mode not enabled.
```

Non-empty whitelist:

```text
Whitelisted users:
  <stored user id> (<current name>, stored name: <stored name>)
Whitelisted groups:
Whitelist only mode active.
```

User and group entries are separate sections. Group operations are not approved by this evidence phase.

## Persistence

A durable EOS whitelist entry remained present after a normal server restart.

The joining player passed the server's whitelist authorization stage, and a later `whitelist list` showed the same stored entry with whitelist-only mode active.

## Noise and Privacy Boundaries

The following output is unrelated to whitelist command completion and must not be returned to Discord:

- `serveradmin.xml` reload lines
- local file-system paths
- LAN or public IP addresses
- authentication-stage details
- unrelated Steam or EOS identifiers
- player positions, health, entity IDs, inventories, or backpack contents
- FPS, memory, chunk, entity, or process statistics
- disconnect or cleanup output
- internal stack traces or socket failures

Platform identifiers are private by default. A future explicitly authorized staff lookup or administration workflow may display requested Steam or EOS identifiers to staff when operationally necessary. Ordinary success and failure responses should avoid echoing identifiers unless that approved staff workflow specifically requires them.

## Scope Exclusions

This evidence does not approve:

- whitelist group add or remove
- fuzzy player matching
- name-only offline administration
- cross-platform identity linking
- public identifier exposure
- arbitrary console execution
- free-form Telnet input
- multiple game servers
